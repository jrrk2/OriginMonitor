Origin control state machines

How OriginHeadless drives the Celestron Origin through a night: the cron launcher, the unattended supervisor, the in-daemon sequencer, the link keeper, and the telescope's own controllers. Each chart shows the outline commands sent, the errors that come back, and what is done about them. Numbers in square brackets point to the other charts. State as of 30 Oct 2026 (branch forecast-outlook).

[0] Overview processes and who talks to whom

Three processes. Cron runs autorun every 10 minutes; it starts the daemon and, once the telescope is initialised (IsAligned and IsReady), launches run. Both talk to the daemon over JSON on 127.0.0.1:8765; only the daemon holds the WebSocket to the telescope.

[1] autorun HeadlessMain.cpp cmdAutorun

Each cron tick does the next missing step and returns. Any gate that fails ends the tick quietly ("idle"); the next tick, 10 minutes later, tries again; a run that ends in failure calls autorun itself 20 s after it exits. Nothing moves before the Sun is below the probe altitude (−7°), and the run itself waits for −12°.

[2] run supervisor: the night HeadlessMain.cpp cmdRun

Plans the night, then walks the plan block by block. Between blocks it reads OriginWatch requests every 30 s. A block is run by the block loop [3]; a skipped block moves on to the next, and Rain, Failed (including three blocks in a row skipped for the same trouble) or Stopped ends the night, which always ends with a park on Polaris and a summary e-mail. A failed run hands back to autorun [1] 20 s after it exits.

[3] block loop: one target HeadlessMain.cpp runTarget

Make sure the telescope is initialised, slew, start the sequencer [5], then a 20 s supervision tick that reads the sequence status and events. Each kind of trouble has its own repair and its own limit, so one fault cannot loop all night; a block that cannot be observed is skipped and the night goes on. The run ends early only for rain, a stop, a fault a reboot did not clear, a telescope gone from the network, or the same trouble three blocks running.

Why “frame never arrived”. The sequencer's watchdog [5] fires at 3 × exposure + 60 s with no image. It has already sent one CancelImaging; the supervisor sends two more and checks the TaskController state each time.
Disconnects. The supervisor no longer reconnects on a fixed sleep; it waits for the daemon's own link keeper [6] and only sends connect itself after 90 s.
Limits. 6 sequence restarts a block (then skip it), 3 re-gotos a block, refocus at most every 20 min and 6 times, 2 reboots and 2 daemon restarts a night, 12 initializes and 6 tube raises a night, backups 3 deep; three blocks in a row skipped for the same trouble end the run.
See [5] sequencer for where the stop reasons come from and [4] reboot recovery for camera_hung.

[4] reboot recovery HeadlessMain.cpp rebootRecover new, not yet exercised by a real hang

For a camera stuck in SAMPLE_CAPTURE that ignores cancels (28 Oct, 00:53). Reboot to System clears it, idle or mid-exposure; tested twice by hand on 28 Oct. The mount comes back unaligned, so recovery has to initialize again, which needs stars.

[5] Sequencer Sequencer.cpp, inside the daemon

The exposure loop. Pipelined: the next RunSampleCapture goes out at the telescope's NewImageReady, so the download and analysis overlap the next exposure. Every stop is a reason string that the block loop [3] reads.

Verdicts from SkyMonitor: clear, hazy, moon_glow, twilight, cloudy, patchy, unknown, off_target, defocused, trailed, no_pointing, unreadable. Trailed and defocused are acted on by the block loop, not here.
Stack side effects. A frame whose filter differs from the stack's archives the old stack and starts a new one. Repeated registration failures replace a bad reference (not in offline restacks).
Stop reasons go to [3] block loop. A disconnect here is followed by [6] link keeper.

[6] link keeper ControlServer.cpp tryReconnect new, tested 28 Oct 13:10

Keeps the daemon's WebSocket up. It acts only on a drop nobody asked for; quit switches it off. Before this, a rebooted telescope left the daemon disconnected until a client sent connect.
